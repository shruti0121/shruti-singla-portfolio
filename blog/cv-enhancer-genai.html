CV Enhancer: Serverless GenAI App (AWS)

Shruti Singla – 3 October 2026
View on GitHub Live demo

Built and deployed a serverless GenAI web app on AWS that rewrites rough resume bullets into stronger, results-focused bullets tailored to a specific job description. Users paste a job description and a few bullets, and the app returns rewritten bullets that use strong action verbs and relevant keywords, without inventing experience, tools, or achievements the person doesn't have.

Architecture

The frontend is a static site stored in a private Amazon S3 bucket and served over HTTPS through Amazon CloudFront using Origin Access Control, with a custom domain on Amazon Route 53 and a certificate from AWS Certificate Manager. The browser calls a REST endpoint on Amazon API Gateway, which invokes a Python AWS Lambda function. The Lambda validates the input, builds the prompt, and calls Claude Haiku 4.5 on Amazon Bedrock through the Converse API, using a US cross-region inference profile. The entire stack is defined in AWS CDK (TypeScript) and deploys with one command.

The design is fully serverless: no VPC, NAT Gateways, load balancers, or containers, so the stack costs almost nothing when nobody is using it. It is also stateless. Users paste resume text, which is personal information, so rather than storing it and then having to secure it, the app keeps nothing. Input goes to the model and the result goes straight back to the browser.

One deployment problem worth solving properly: the frontend needs the API URL, but the URL doesn't exist until the stack is deployed. Instead of hardcoding it, CDK generates a config.json file with the real URL during deployment and uploads it to the S3 bucket alongside the site. The frontend reads it on load, so anyone who deploys the stack to their own account automatically gets the correct URL.

Prompt engineering and evaluation

Connecting the AWS services was the easy part. The real work was making the model produce useful, consistent, and honest output. The system prompt sets strict rules: start each bullet with an action verb, focus on impact, keep the same number of bullets, return only the bullets, and never invent experience, tools, or achievements. The rules live in the system prompt, separate from the user's input, so users can't easily override them.

There is no off-the-shelf benchmark for "is this a good resume bullet," so I built my own evaluation suite: 16 test cases covering vague bullets, bullets with metrics that must be preserved, bullets with no metrics that must not gain any, an already-strong bullet, non-tech roles like nursing and sales, formatting edge cases, and prompt injection attempts hidden in both the bullets and the job description. A Python script sends each case to Bedrock with the same prompt and settings as the deployed Lambda, then checks the output automatically for bullet count, format, new numbers, and case-specific forbidden phrases. Each case runs several times, since outputs vary between runs.

The eval caught a real problem. For a barista applying to a cloud engineering job, the model rewrote "made coffee drinks for customers" as "architected and deployed serverless solutions using AWS Lambda." The original instruction to use job keywords "where they honestly apply" wasn't strong enough when the experience didn't match. I added rules requiring each bullet to describe the same task as the original and to highlight transferable skills instead of borrowing the job description's tools, and the eval confirmed the fix.

It also flagged a judgment call. The model turned "grew monthly revenue from $8,000 to $12,500" into "drove 56% revenue growth." The check marked 56 as a new number, but on review it was a correct calculation from the user's own figures. I decided to allow it, since it strengthens the bullet using only the user's data, and I review that case by hand on each run because LLM arithmetic isn't guaranteed.

Security and cost

Every request to the public API costs money on Bedrock, so cost control is built in at several levels: API Gateway throttling stops scripts from running up the bill, input size limits and a cap on response tokens keep each request small and predictable, an AWS Budgets alert warns of unexpected spend, and Claude Haiku 4.5 was chosen because it is fast and inexpensive for a task that doesn't need a larger model.

The Lambda runs with a least-privilege IAM role that can only write its logs and invoke Bedrock models. CORS is restricted to the app's own domain. Input is validated twice: in the browser for instant feedback, and in the Lambda before any call to Bedrock, because the frontend can always be bypassed. On failure, full error details go to CloudWatch Logs while users see a generic message, so internal details are never exposed.
